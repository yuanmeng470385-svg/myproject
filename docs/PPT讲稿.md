## 第 1 页：封面

**标题**：健康小云 —— AI 健康助手 · 跨平台移动应用

**副标题**：Flutter Android + Vue 3 Web + FastAPI 后端

**讲稿**：

大家好，我带来的项目是「健康小云」—— 一款 AI 驱动的健康助手应用。

它的核心能力是：用户可以通过**文字对话**和**实时语音/视频通话**向 AI 咨询健康问题。系统会在这个过程中自动沉淀用户的健康画像和长期记忆，让每一次交流都更懂你。

项目覆盖 **Android 移动端和 Web 端两个平台**，对接统一的 Python 后端和阿里云百炼大模型，在 16 周内从零交付了完整的跨平台方案。

## 第 2 页：项目背景与问题 🎯

**标题**：为什么做健康小云？

**讲稿**：

做这个项目，源于三个现实痛点：

**第一，健康咨询的门槛**。大多数人身体不舒服时，第一反应是百度搜索，但搜出来的信息不专业、不成体系，甚至越搜越焦虑。真正去医院咨询又需要预约、排队，成本很高。

**第二，现有 AI 助手的短板**。市面上有很多 AI 聊天产品，但它们大多是一次性对话，不会记住你是谁、有什么健康问题、上次聊过什么。每次对话都从零开始，缺乏个性化。

**第三，多端覆盖的需求**。除了在手机上装 App，很多用户希望在电脑浏览器上也能直接使用健康助手——不用安装、打开即用。我们采用了一套「同一后端，双端交付」的方案：Flutter 做原生移动端体验，Vue 3 做 Web 端即时访问，两个端共享同一套 AI 能力和数据。

**我们的目标**：做一款随时随地可用的 AI 健康助手，温和、专业、可追溯。记住用户说过的话，持续沉淀成有价值的健康画像。

## 第 3 页：核心功能总览 🎯

**标题**：健康小云能做什么？

**讲稿**：

健康小云围绕「AI 健康咨询」这条主线，提供了六大核心功能：

1. **登录与认证**：手机号注册登录，JWT 鉴权，个人数据完全隔离。
2. **AI 文字咨询**：支持多轮对话，实时流式输出——就是字一个字往外蹦，不用等整个回答生成完才显示。内容用 Markdown 渲染，支持标题、列表、加粗。AI 还会自动生成跟问建议。
3. **用户画像与长期记忆**：系统会自动从对话中提取事实——比如你说「我最近血压偏高」「我有糖尿病家族史」——去重后写入长期记忆。下一次对话时，这些信息会和你的健康记录一起注入 AI 的上下文，让回答更个性化。
4. **对话历史**：历史对话列表，支持详情查看、删除、AI 自动生成摘要标题。如果标题不满意，一键重新生成。
5. **实时语音/视频通话**：像打电话一样和 AI 交流。支持打断、回声消除、语音转录自动保存。视频通话时摄像头画面实时传给 AI 做视觉识别。
6. **深色模式**：Material Design 3 规范，奶油暖调配色，支持深浅主题一键切换。

## 第 4 页：技术栈 🎯

**标题**：用什么技术实现的？

**讲稿**：

项目涉及三个技术端，每个端的选型都有考量：

**Flutter Android 端**：
- 语言是 Dart，状态管理用 flutter_bloc（BLoC 模式）——这是 Google 推荐的模式，单向数据流，每个功能模块拆成 event / state / bloc 三个文件，职责清晰。
- 网络层：dio 做 HTTP 请求，web_socket_channel 做 WebSocket 实时通信，SSE 客户端做流式接收。
- 路由用 go_router 的 ShellRoute 实现底部导航。
- 音频和摄像头通过 Dart 条件导入实现平台适配——Android 用原生 AudioRecord/AudioTrack+CameraX，Web 用浏览器 getUserMedia。

**Vue 3 Web 端**：
- TypeScript + Vite 构建，Pinia 状态管理，vue-router 路由。
- 聊天流式用原生 fetch + ReadableStream 解析 SSE，打字机逐字效果。
- 语音通话基于浏览器 AudioContext + getUserMedia，无需安装任何插件。
- AI 回答用 marked + DOMPurify 做 Markdown 安全渲染。

**后端**：
- FastAPI 高性能异步框架，SQLAlchemy ORM 操作 PostgreSQL。
- JWT 认证，密码 bcrypt 哈希。
- AI 能力全部对接阿里云百炼：文本对话用 qwen3-omni-flash，实时语音用 qwen3.5-omni-plus-realtime。

## 第 5 页：系统架构 🎯

**标题**：整体架构怎么设计的？

**讲稿**：

这是整体的架构图——

两个客户端（Flutter 和 Web）通过 HTTP / SSE / WebSocket 三种协议，走 JWT 认证，统一对接 FastAPI 后端。

后端按照 FastAPI 的标准分层：router 负责路由、service 负责业务逻辑、model 负责数据库映射、schema 负责请求响应的数据校验。

AI 这一层，后端扮演"桥接"角色：文本对话走 HTTP 流式调用，语音通话走 WebSocket 双向桥接——把客户端的音频实时转发给 DashScope，再把 AI 的音频和文本实时转发回来。

数据库是 PostgreSQL，存用户、对话、消息、健康记录、长期记忆、用户画像。

**Flutter 客户端内部**采用 Clean Architecture 分层：最外层 presentation 是 UI 和 BLoC，中间 domain 是纯抽象的仓库接口，内层 data 是接口的具体实现，最底层 core 是跨层共享的网络、存储、音频、摄像头等基础设施。

依赖方向是 presentation → domain ← data，domain 不依赖任何框架，方便测试和替换实现。

## 第 6 页：关键实现 —— AI 流式对话

**标题**：AI 文字对话的流式输出是怎么做的？

**讲稿**：

AI 文字对话的技术核心是 **SSE 流式输出**。

传统做法是：发请求 → 等服务端全部生成完 → 一次性返回 → 前端渲染。用户盯着空白屏幕等 5 到 10 秒，体验很差。

我们的做法是：前端发 POST 请求到 `/api/consult/chat/stream`，带 `Accept: text/event-stream` 头。后端用 FastAPI 的 `StreamingResponse`，把 AI 每生成一个 token 就立马往外推——格式是 `data: {json}\n\n`，最后发 `data: [DONE]\n\n` 表示结束。

Flutter 端用 `SSEClient` 解析事件流，每收到一个 delta 就更新 BLoC 状态，UI 层实时重绘最后一条 AI 消息。用户看到的是打字机效果——逐字输出，体验很流畅。

这里有个坑：SSE 传输过程中，TCP 分块可能在 3 字节的 UTF-8 中文字符中间切断，导致 JSON 解析失败、丢字。我们的解法是：不逐块解码，而是把迄今收到的所有字节累积起来整体解码，已收到结尾标识 `\n\n` 的事件字节必然是完整的。

流程的收尾：AI 生成完毕后，后端自动把用户消息和 AI 回复持久化到数据库，通过 SSE 回传 conversation_id。前端拿到后存起来，下次继续聊。

## 第 7 页：关键实现 —— 实时语音/视频通话 🎯

**标题**：语音/视频通话是怎么实现的？

**讲稿**：

语音通话是技术难度最高的模块。

**整体链路**：Flutter 客户端通过 WebSocket 连到后端 voice.py，后端再通过另一个 WebSocket 连到阿里云百炼的 Realtime API。后端扮演"透明桥接"——双向转发音频和事件。

**音频上行**：客户端麦克风以 16kHz 单声道 PCM 格式采集，每 100 毫秒一帧，base64 编码后通过 WebSocket 发送 `audio` 类型消息。后端转发给 DashScope 的 `input_audio_buffer.append`。

**音频下行**：DashScope 生成音频 delta（24kHz PCM），后端转发给客户端，客户端用 AudioTrack（Android）或 AudioContext（Web）实时播放。

**VAD 自动断句**：我们不用手动按按钮说话。DashScope 内置了 semantic VAD——语义级语音活动检测。它能判断用户什么时候开始说话、什么时候说完。用户说完后自动提交音频缓冲区给 AI 处理，全程自动。

**打断机制**：AI 在说话时用户可以随时打断。VAD 检测到用户开口 → DashScope 发 `speech_started` → 后端立即 `response.cancel` 取消 AI 回复 + `clear` 音频缓冲区 → 客户端切换回收音状态。整个过程 200 毫秒以内。

**回声处理**：模拟器上没有硬件回声消除，扬声器声音会被麦克风重新采集形成回声循环。我们的方案是三级音频控制：AI 说话时麦克风完全静音，等待用户时开噪声门压低环境音，用户说话时才全量收音。

**视频帧**：摄像头以每秒 1 帧的频率抓 JPEG 帧（480p），base64 后发送给后端，后端转发给 DashScope 做视觉识别。

**持久化**：AI 的完整转录（`audio_transcript.done`）和用户的语音转录（`input_audio_transcription.completed`）自动保存到对话的消息表。通话结束后用户可以查看完整的文字记录。

## 第 8 页：关键实现 —— 用户画像与长期记忆

**标题**：如何让 AI 越来越懂用户？

**讲稿**：

这是健康小云区别于普通 AI 聊天产品的核心功能。

**三层上下文注入**：

第一层，**健康记录**：用户可以手动录入血压、血糖、体重等数据，系统按类型查询并聚合。

第二层，**长期记忆**：AI 在对话过程中自动提取用户说的事实——「我最近睡眠不好」「有高血压家族史」「对青霉素过敏」——经过重要性评分和去重后，写入 Memory 表。

第三层，**用户画像**：系统定期根据记忆和对话，由 AI 生成一个结构化画像——性别、年龄、身高、体重、健康摘要、风险标签。

**每次对话前**，后端的 MemoryService 会把这三层信息加上最近的对话历史，一起注入到 AI 的 system prompt 中。这样 AI 不需要用户重复说过的话，回答更有针对性。

**去重逻辑**很关键——同一个事实用户可能多次提到（今天说睡眠不好，明天又说），我们用语义相似度和类别匹配来避免重复存储。

## 第 9 页：视觉设计系统 🎯

**标题**：奶油暖调 · 哑光鼠尾草 —— 设计语言

**讲稿**：

项目的视觉设计经历了完整的 redesign。

**设计理念**：健康类产品常见的是蓝绿色冷调「医疗感」。我们刻意避开这个方向，选择了「奶油暖调 + 哑光鼠尾草」——温暖、安静、不焦虑。用户打开 App 应该是放松的，不是紧张的。

**Token 化体系**：所有颜色、字体、圆角、阴影、动效参数都集中在 `core/constants/` 下，以 token 类暴露。新增 UI 一律引用 token，不写裸 hex 值。好处是一处改动全局生效——比如要调主色饱和度，只改一个 token，整个 App 自动跟着变。

- **颜色**：主色鼠尾草 `#7FB3A8`、背景燕麦奶油 `#F6F4EE`、点缀暖砂 `#B9A88F`、文字暖墨色阶。
- **字体**：大标题用 NotoSerifSC 宋体（中文）+ Fraunces（英数），正文用系统无衬线体。
- **动效**：静润曲线 `Cubic(0.22, 0.61, 0.36, 1)`，强缓出、无回弹。入场动画是「淡入 + 上浮」，每个元素按 index 错峰出场。

**深色模式**的实现是技术难点。我们的方案是「调色板动态化」——AppColors 从 static const 改为运行时的 getter，切换深色时只改底层色板对象引用，全项目颜色引用不用改一行。通过 `MaterialApp.builder` 的 `KeyedSubtree` 重建 Navigator 子树，避免 GoRouter 的 GlobalKey 冲突。

## 附录：可能被问到的问题（Q&A 预案）

### Q1: 为什么不直接用 WebView 或 RN 做跨平台？

R: WebView 做不到原生级别的音频/摄像头性能，实时通话延迟不可控。而且我们选 Flutter 做移动端正是因为它的原生性能和对多媒体硬件的直接访问能力。Web 端作为补充覆盖了桌面场景——用户不用装 App 就能用。

### Q2: 语音通话的延迟怎么样？

R: 网络延迟主要取决于后端到 DashScope 的 WebSocket 链路。本地音频采集 100ms 一帧，编解码几乎没有延迟。打断响应在 200ms 以内。整体体验接近真人电话。

### Q3: 长期记忆怎么保证准确性？

R: 去重逻辑做了两重保护——语义相似度比较 + 同类别覆盖。AI 提取事实时带 importance 评分，低分的不入库。用户也可以手动删除不想要的记忆条目。

### Q4: 后端能支撑多少并发？

R: FastAPI 是异步框架，单进程可以支撑数百并发连接。语音通话是瓶颈——每个通话独占一个 DashScope WebSocket 连接，受 API 配额限制。生产环境可以通过 uvicorn workers 水平扩展，PostgreSQL 连接池管理。

### Q5: AI 输出的内容安全吗？会不会给出错误的医疗建议？

R: 这是一个重要的边界。我们在 system prompt 中明确了 AI 的定位——健康助手，不是医生。AI 的回答会以「建议咨询专业医生」收尾。不会开药方、不会下诊断。所有对话记录可追溯。
